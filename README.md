# Berdanka-test

Проект для `Arduino UNO R4 WiFi` с IMU (`ICM-20948`) и TFT (`ILI9488`), который:
- читает ориентацию устройства (roll/pitch/yaw) из DMP;
- принимает команды по TCP от ПК/Jetson;
- рисует на экране квадрат-цель относительно текущего положения;
- показывает состояние IMU/TCP и диагностику в Serial;
- поддерживает Windows GUI с YOLO (опционально) для автоматической отправки углов.

---

## 1. Что делает проект

### 1.1 Основной сценарий
1. Arduino поднимает Wi-Fi AP (`SSID/PASS` в `src/main.cpp`).
2. Arduino запускает TCP сервер на порту `3333`.
3. Клиент (Windows/Jetson) подключается и отправляет пакеты формата:
   - `MSG:<text>;X:<pitchDeg>;Y:<yawDeg>\n`
4. Arduino парсит пакет, сохраняет `spawnPitch/spawnYaw`.
5. В каждом цикле Arduino:
   - читает IMU;
   - вычисляет относительные углы до цели;
   - рисует квадрат на TFT;
   - показывает статус TCP (`TCP OK` / `TCP WAIT`);
   - пишет отладку в Serial с ограниченной частотой.

### 1.2 Что видно на экране TFT
- Центр (прицел) и HUD-строки:
  - `Roll`, `Pitch`, `Yaw`;
  - `Msg`, `IP`;
  - статус IMU (`IMU INIT...`, `IMU INIT FAIL`, `IMU OK`);
  - статус TCP (`TCP WAIT` или `TCP OK`).
- Квадрат-цель:
  - цвет: зеленый в допуске, красный вне допуска;
  - `TCP WAIT`: квадрат полый;
  - `TCP OK`: квадрат залитый.

## 2. Структура репозитория

- `src/main.cpp`  
  Основная прошивка Arduino: IMU, Wi-Fi AP/TCP, рендер UI и логика квадрата.

- `platformio.ini`  
  Конфигурация сборки `PlatformIO` для `uno_r4_wifi`.

  Windows GUI (Tkinter): Wi-Fi connect через `netsh`, TCP клиент, ручная отправка, опционально камера + YOLO + автопередача центра.

- `tools/jetson_tcp_gui.py`  
  Jetson/Linux GUI (Tkinter): Wi-Fi connect через `nmcli`, TCP клиент, ручная отправка.

- `yolo11n.pt`  
  Локальная модель YOLO для опционального режима в Windows GUI.

## 3. Архитектура и поток данных

`IMU(DMP) -> Arduino loop -> angle processing -> TFT draw`

`Windows/Jetson GUI -> TCP packet -> Arduino parser -> spawn angles -> relative target draw`

Важный момент: координаты в GUI и в прошивке согласованы через явный swap осей в `loop()`:
- после чтения IMU выполняется `roll <-> pitch`.

Это сделано, потому что физическая ориентация сенсора/монтажа обычно не совпадает с экранной системой координат.

## 4. Протокол TCP

### 4.1 Формат пакета
Ожидается одна строка:

```text
MSG:<message>;X:<number>;Y:<number>\n
```

Пример:

```text
MSG:PHONE;X:-3.50;Y:170.00
```

### 4.2 Валидация на Arduino
- `MSG:` должен быть в начале строки;
- обязательны `;X:` и `;Y:`;
- `X`/`Y` содержат только цифры, знак и точку;
- пустые значения отвергаются.

Если пакет невалидный:
- Arduino отвечает `ERR;BAD_PACKET;<line>`.

ACK-пакет на успешный приём:
- по умолчанию отключен (`ENABLE_PACKET_ACK=false`) для снижения лагов;
- можно включить обратно, если нужен строгий handshaking.

## 5. Алгоритмы (и почему так)

### 5.1 Чтение ориентации из DMP
Используется `GAME_ROTATION_VECTOR` из `ICM-20948`.
Из кватерниона вычисляются Euler углы:
- `roll = atan2(...)`
- `pitch = asin(...)`
- `yaw = atan2(...)`

Почему DMP:
- меньше вычислений на MCU;
- устойчивее, чем «сырой» интеграл гироскопа без фильтра.

### 5.2 Нулевая калибровка при старте
Первое валидное чтение фиксируется как `zeroRoll/zeroPitch/zeroYaw`, далее вычитается.

Почему:
- пользователю не нужно вручную калибровать каждый запуск;
- «нулевая поза» становится текущим положением на старте.

### 5.3 Нормализация углов и устранение перескока ±180
Используются:
- `wrapAngle180f/i` — приведение в диапазон `(-180, 180]`;
- `deltaAngle180f/i` — минимальная разница на окружности.

Почему:
- устраняет баг «квадрат исчезает/улетает» при переходе через `+180/-180`.

### 5.4 Антидрифт yaw (hold)
Если изменение yaw меньше порога `yawDriftLimitDeg` дольше `yawHoldTime`, yaw фиксируется.

Почему:
- снижает дрожание в покое;
- уменьшает микроскопические колебания целеуказателя.

### 5.5 Freeze yaw около gimbal-lock
При `|pitch|` выше порога yaw не обновляется свободно.

Почему:
- вблизи экстремальных наклонов yaw становится менее устойчивым;
- фиксация предотвращает визуальные скачки.

### 5.6 Квантование углов
Углы округляются шагом `ANGLE_STEP_DEG=2`.

Почему:
- меньше шум и дрожание HUD/квадрата;
- меньше частота фактических изменений UI.

### 5.7 Рендер квадрата
Алгоритм:
1. Преобразование `deg -> px` (`PX_PER_DEG`);
2. Расчет центра квадрата относительно экрана;
3. Ограничение выхода за края с гарантией видимой кромки (`EDGE_VISIBLE_PX`);
4. Клиппинг `clipRect`;
5. Инкрементальная перерисовка (сравнение с прошлой позицией/цветом/стилем).

Почему:
- не перерисовывать весь экран;
- минимизировать SPI-нагрузку и снизить input lag.

### 5.8 Ограничение частот «тяжелых» операций
- TCP состояние опрашивается раз в `TCP_POLL_MS`;
- квадрат рисуется не чаще `BOX_REFRESH_MS` (~30 FPS);
- debug в Serial раз в `SERIAL_DEBUG_MS`.

Почему:
- `client.connected()` и TFT-операции — дорогие;
- частый Serial log также блокирует MCU.

## 6. Константы и обоснование значений

Ниже ключевые группы и смысл. Значения подобраны как компромисс между отзывчивостью и стабильностью.

### 6.1 Сеть
- `WIFI_SSID="cisco"`, `WIFI_PASS="cisco1234"`  
  AP-параметры Arduino. Пароль WPA2 должен быть 8+ символов.

- `SERVER_PORT=3333`  
  Порт TCP-сервера. Оставлен простым и фиксированным для GUI.

### 6.2 Экран и геометрия
- `SCREEN_W=480`, `SCREEN_H=320`, `TFT_ROTATION=1`  
  Физическая ориентация дисплея ILI9488.

- `PX_PER_DEG=3.0`  
  1° ≈ 3 пикселя. Дает заметную динамику без слишком резких смещений.

- `BOX_SIZE=50`  
  Размер маркера: хорошо виден на 480x320, но не «закрывает» центр.

- `EDGE_VISIBLE_PX=5`  
  Квадрат частично остаётся видимым у границы, пользователь понимает направление.

### 6.3 Углы и попадание в цель
- `ANGLE_STEP_DEG=2`  
  Шаг квантизации для визуальной стабильности.

- `TARGET_TOL_DEG=6`  
  Допуск попадания. Меньше — нервно, больше — слишком «мягко».

### 6.4 Тайминги
- `HUD_REFRESH_MS=10000`  
  Период принудительного полного обновления HUD как страховка от артефактов.

- `TCP_STATUS_REFRESH_MS=200`  
  Частота обновления строки TCP (достаточно быстро для UX, недорого).

- `TCP_POLL_MS=80`  
  Уменьшает нагрузку от частых проверок `connected()`, сохраняя быстрый reconnection.

- `BOX_REFRESH_MS=33`  
  Кэп ~30 FPS для отрисовки квадрата.

- `SERIAL_DEBUG_MS=2000`  
  Редкий debug-лог, чтобы не тормозить цикл.

### 6.5 Флаги режима
- `ENABLE_SERIAL_DEBUG=true`  
  Быстрый переключатель отладки без удаления кода.

- `ENABLE_PACKET_ACK=false`  
  Отключен по умолчанию для минимизации Wi-Fi блокировок в real-time режиме.

### 6.6 Стабилизация yaw
- `yawDriftLimitDeg=0.05`, `yawHoldTime=250`  
  Подавление микродрифта в покое.

- `pitchLockThreshold=80`  
  Защита от нестабильного yaw при близости к граничным углам pitch.

## 7. Запуск проекта

## 7.1 Требования
- Arduino UNO R4 WiFi
- IMU ICM-20948 (I2C)
- TFT ILI9488 (SPI)
- PlatformIO
- Python 3.10+ (для GUI)

Для Windows GUI (опционально YOLO):
- `opencv-python`
- `ultralytics`
- `pillow`

### 7.2 Сборка и прошивка Arduino

В корне проекта:

```bash
pio run
pio run -t upload
pio device monitor -b 115200
```

Если `pio` не в PATH, используйте установку PlatformIO из VSCode.

### 7.3 Запуск Windows GUI

```bash
python tools/windows_tcp_gui.py
```

Последовательность:
1. В GUI нажать `Connect Wi‑Fi (netsh)`.
2. Проверить, что ПК получил IP `192.168.4.x`.
3. Нажать `Connect` к `192.168.4.1:3333`.
4. Отправлять вручную (`Message/X/Y`) или включить YOLO-режим.

### 7.4 Запуск Jetson GUI

```bash
python3 tools/jetson_tcp_gui.py
```

Последовательность:
1. Подключить Wi-Fi через `nmcli` (из GUI).
2. Указать актуальный IP Arduino.
3. Нажать `Connect`.
4. Отправлять `MSG/X/Y`.

## 8. Производительность и задержки

По измерениям Serial `DBG`:
- `tcp=WAIT`: цикл может быть ~7–8 ms;
- `tcp=OK` без активных изменений: ~15–17 ms;
- при активной динамике и частой перерисовке возможны пики десятки миллисекунд.

Основные источники лагов:
1. TFT-операции (`fillRect/drawRect/line`) — дорогие по SPI.
2. Сетевой стек WiFiS3 при активном сокете.
3. Частый Serial лог.

Что уже сделано:
- throttling TCP poll;
- throttling box redraw;
- снижена частота debug;
- ACK отключен по умолчанию.

---

## 9. Почему некоторые решения выбраны именно так

- **`String` для парсинга TCP**  
  Проще поддерживать и читать. Минус: потенциальная фрагментация heap в очень долгих сессиях.

- **Дифференциальный рендер, а не full redraw экрана**  
  Существенно меньше лагов и мерцания.


- **Полый квадрат при `TCP WAIT`**  
  Мгновенная визуальная индикация отсутствия связи без чтения текста.
